# InfoFlow AI

**Единая база знаний, которая сама делает резюме, теги и ищет по смыслу.**

InfoFlow AI решает проблему фрагментации рабочей информации: заметки, ссылки, файлы и идеи обычно разбросаны по Telegram, закладкам, Notion и почте. Проект собирает всё в одном месте, автоматически обрабатывает материал с помощью AI и позволяет находить его гибридным поиском — по ключевым словам и по смыслу одновременно.

Доступны два клиента: **веб-интерфейс** и **Telegram-бот**. Оба работают с одной базой и одним конвейером обработки.

## Что умеет

- **Сохраняет ссылки, заметки и файлы** — через веб-интерфейс, Telegram или API.
- **Извлекает текст** из веб-страниц (напрямую или через Jina Reader), PDF, HTML, TXT, MD, CSV, JSON и других текстовых форматов.
- **Делает AI-резюме** на 2–3 предложения и **автоматически подбирает 3–5 тегов**.
- **Строит эмбеддинги и чанки** для длинных документов, чтобы не терять контекст.
- **Ищет гибридно**: BM25 по ключевым словам + косинусное сходство векторов + Reciprocal Rank Fusion.
- **Фильтрует** результаты по типу записи и тегу.
- **Изолирует данные пользователей** на уровне реляционной БД и векторного хранилища.
- **Работает из коробки без внешних сервисов**: SQLite, hash-эмбеддинги и локальная эвристика для резюме.
- **Подключает внешние AI-провайдеры**: OpenRouter, Ollama, любой OpenAI-совместимый endpoint.
- **Обрабатывает голосовые сообщения** в Telegram (при наличии сервиса транскрипции).
- **Показывает статус обработки** (`pending → processing → ready / failed`) и позволяет перезапустить обработку.
- **Масштабируется опционально**: PostgreSQL, ChromaDB, Celery + Redis, sentence-transformers.

### Пользовательские сценарии

1. **Быстрое сохранение ссылки.** Пользователь вставляет URL и нажимает «Сохранить в InfoFlow». Система скачивает страницу, делает резюме, подбирает теги и добавляет запись в библиотеку.
2. **Семантический поиск.** Запрос «как настроить аутентификацию через JWT» находит заметку про «токены доступа и безопасность», даже если слова «JWT» в тексте не было.
3. **Идея на ходу.** Пользователь отправляет текст, ссылку, PDF или голосовое сообщение в Telegram-бота. Материал расшифровывается, анализируется и становится доступен в веб-интерфейсе.

## Быстрый старт

### Требования

- Python **3.11+** (рекомендуется 3.12/3.13)
- pip
- Опционально: PostgreSQL, Redis, ChromaDB, Ollama, токены OpenRouter/Telegram/Jina

### Установка

```bash
# 1. Виртуальное окружение
python -m venv .venv

# Windows
.venv\Scripts\activate
# Linux / macOS
source .venv/bin/activate

# 2. Зависимости
pip install -r requests.txt

# 3. Конфигурация (можно не менять — значения по умолчанию рабочие)
copy .env.example .env      # Windows
cp .env.example .env        # Linux / macOS

# 4. Запуск
python run.py
# или
uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

Откройте:

- Веб-интерфейс — <http://127.0.0.1:8000/>
- Swagger UI — <http://127.0.0.1:8000/docs>
- ReDoc — <http://127.0.0.1:8000/redoc>
- Health-check — <http://127.0.0.1:8000/health>

При первом запуске автоматически создаются каталог `data/` и таблицы SQLite (`AUTO_CREATE_TABLES=true`).

### Регистрация

Откройте веб-интерфейс, переключитесь на вкладку регистрации и создайте аккаунт. Пароль — минимум 8 символов. После входа появится библиотека и форма сохранения материала.

Кнопка **«Читать»** или клик по карточке открывает окно с AI-резюме, полным извлечённым текстом, тегами, ссылкой на источник и действиями. Там же можно скопировать текст и вручную исправить теги — сохранённый список заменит и автоматические, и ручные теги.

```
        │              FastAPI (API)              │
        │  Auth │ Ingestion │ Search │ Processing │

                │               │
     ┌──────────▼───────┐   ┌───▼──────────────────┐
     │  SQLAlchemy      │   │  Фоновая обработка   │
     │  SQLite /        │   │  BackgroundTasks /   │
     │  PostgreSQL      │   │  Celery + Redis      │
     └──────────────────┘   └──────────┬───────────┘
                                       │
                    ┌──────────────────▼──────────────────┐
                    │  AI → chunking → embeddings → store │
                    │  OpenRouter/Ollama/эвристика        │
                    │  ChromaDB / локальный SQLite        │
                    └─────────────────────────────────────┘
```

Конвейер обработки записи:

```
создание записи
   → извлечение текста (Jina / httpx + BeautifulSoup / pypdf)
   → AI-резюме и теги (OpenRouter / Ollama / OpenAI-совместимый API / эвристика)
   → очистка и chunking (аналог RecursiveCharacterTextSplitter)
   → эмбеддинги (sentence-transformers / Ollama / hash)
   → запись векторов с фильтром по user_id
   → статус ready
```

Если внешний сервис недоступен, обработка не падает: используются локальная эвристика и hash-эмбеддинги, а ошибка фиксируется в логах.

## Как работает поиск

Реализованы три режима.

### `keyword` — BM25

- Текст записи разбивается на чанки; заголовок, теги и резюме добавляются в контекст каждого чанка.
- Используется BM25 (`k1=1.5`, `b=0.75`) с лёгкой нормализацией словоформ и стоп-словами.
- Дополнительные бусты: совпадение с заголовком, тегами и точная фраза в заголовке.
- Лучший чанк записи формирует сниппет.

### `semantic` — косинусное сходство

- Запрос превращается в вектор тем же эмбеддером, что и документы.
- Векторное хранилище возвращает ближайшие чанки **только текущего пользователя**.
- Лучший результат по каждой записи попадает в выдачу.
- Слабые совпадения отсекаются: абсолютный порог `SEARCH_SEMANTIC_MIN_SCORE`, относительный — `SEARCH_SEMANTIC_RELATIVE_CUTOFF` (результат не слабее лучшего более чем в N раз).
- Для офлайн-фолбэка `hash` дополнительно проверяется лексическое покрытие запроса: запись без общих слов с запросом не попадает в выдачу, поэтому режим не возвращает «всё подряд».

### `hybrid` — Reciprocal Rank Fusion

Списки `keyword` и `semantic` объединяются без подбора весов:

```
score = Σ 1 / (k + rank),  k = 60
```

Итоговый score нормализуется в диапазон `0..1`, а поле `match` показывает, каким способом найдена запись: `keyword`, `semantic` или `hybrid`. RRF устойчив к разной шкале BM25 и косинусного сходства.

Порядок выдачи не зависит от того, в каком приложении сохранена запись — веб и Telegram используют один и тот же поиск.

## AI-обработка

`app/services/ai.py` поддерживает:

1. **OpenRouter** — основной облачный провайдер (OpenAI-совместимый API).
2. **Ollama** — локальная модель, данные не покидают машину.
3. **Произвольный OpenAI-совместимый endpoint** — LM Studio, vLLM, локальный шлюз и т. п.
4. **Локальная эвристика** — всегда доступный фолбэк: первые предложения текста становятся резюме, частотные значимые слова — тегами.

Модель получает системный промпт с требованием вернуть строго JSON:

```json
{"title": "...", "summary": "...", "tags": ["...", "..."]}
```

Промпт явно запрещает выполнять инструкции из анализируемого материала — текст рассматривается только как данные. При ошибке сети, пустом ответе или невалидном JSON срабатывает эвристика, поэтому сохранение никогда не блокируется из-за AI.

**Транскрипция голосовых** использует OpenAI-совместимый `/audio/transcriptions` (`TRANSCRIPTION_BASE_URL`, `TRANSCRIPTION_API_KEY`, `TRANSCRIPTION_MODEL`).

## Эмбеддинги и векторное хранилище

### Эмбеддинги

- `EMBEDDING_PROVIDER=auto` — sentence-transformers, если пакет установлен, иначе hash.
- `sentence` / `local` — реальные семантические эмбеддинги.
- `ollama` — локальный Ollama (`/api/embed`, с фолбэком на старый `/api/embeddings`).
- `hash` — детерминированный офлайн-фолбэк: bag-of-words + символьные триграммы, L2-нормализация.

Hash-векторы не понимают синонимы, но позволяют проекту работать сразу после установки и честно участвуют в гибридном поиске. Для полноценного семантического поиска установите `sentence-transformers` или подключите Ollama.

### Векторное хранилище

- `VECTOR_BACKEND=auto` — ChromaDB, если установлена, иначе локальное SQLite-хранилище.
- `chroma` — персистентная коллекция ChromaDB с `hnsw:space=cosine`.
- `local` — таблица `vectors` в SQLite с BLOB-векторами и косинусным перебором.

В обоих бэкендах каждый запрос фильтруется по `user_id`, поэтому пользователи не видят чужие векторы и результаты поиска. При удалении записи удаляются её чанки, векторы и загруженный файл.

## Celery и Redis

По умолчанию обработка выполняется через FastAPI `BackgroundTasks`: этого достаточно для локального запуска и небольшой нагрузки. Для отдельного worker'а включите очередь:

```env
USE_CELERY=true
REDIS_URL=redis://localhost:6379/0
```

Установка и запуск:

```bash
pip install celery redis
celery -A app.workers.celery_app.celery_app worker --loglevel=info
```

Если Celery или Redis недоступны, приложение не теряет задачу: оно логирует предупреждение и обрабатывает запись в фоне текущего процесса.

## Docker

```bash
# 1. Подготовьте переменные (секрет и, при необходимости, ключи API)
copy .env.example .env

# 2. Соберите и запустите: PostgreSQL + Redis + FastAPI + Celery worker
docker compose up --build

# 3. Откройте http://localhost:8000
```

Контейнер `app` при старте выполняет `alembic upgrade head` и запускает Uvicorn. Worker обрабатывает очередь Celery. Данные PostgreSQL, Redis и приложения хранятся в именованных volume'ах.

Telegram-бот запускается отдельным профилем:

```bash
docker compose --profile bot up --build
```

По умолчанию Docker-образ использует hash-эмбеддинги и локальное векторное хранилище, чтобы сборка оставалась быстрой. Если нужны sentence-transformers и ChromaDB:

```bash
docker build --build-arg INSTALL_OPTIONAL=true -t infoflow:full .
```

Тяжёлые модели лучше монтировать или кешировать отдельно — образ с ними занимает несколько гигабайт.

## Безопасность и изоляция данных

- **Пароли**: PBKDF2-HMAC-SHA256, 260 000 итераций, случайная соль, сравнение через `hmac.compare_digest`.
- **JWT**: HS256, срок жизни по умолчанию 7 дней, проверка подписи, срока и типа токена.
- **Изоляция**: все запросы к записям, тегам, статистике и поиску фильтруются по `user_id`; векторные запросы также ограничены пользователем. Чужая запись возвращает `404`.
- **SSRF-защита**: запрещены localhost, приватные, loopback, link-local и служебные адреса; нестандартные порты закрыты, если не включён `ALLOW_PRIVATE_URLS`.
- **Файлы**: ограничение размера (`MAX_UPLOAD_MB`), безопасное имя, удаление файла только внутри `UPLOAD_DIR`.
- **CORS**: настраивается через `CORS_ORIGINS`.
- **Секреты**: ключи хранятся только в `.env`, который исключён из git.

Перед production обязательно:

1. Замените `SECRET_KEY` на длинную случайную строку.
2. Включите HTTPS.
3. Ограничьте `CORS_ORIGINS` конкретным доменом.
4. Выключите `ALLOW_PRIVATE_URLS`.
5. Настройте резервное копирование `data/` и PostgreSQL.

Ограничения текущей реализации: JWT хранится в `localStorage` браузера, нет rate limiting и refresh-токенов. Для публичного production-развёртывания стоит добавить httpOnly-cookie, лимиты запросов и CSRF-защиту.

## Ограничения и планы

**Ограничения**

- Hash-эмбеддинги не заменяют настоящую семантику: для качества нужны sentence-transformers или Ollama.
- Локальное векторное хранилище перебирает векторы в памяти процесса — подходит для небольших библиотек; для больших объёмов используйте ChromaDB.
- PDF без текстового слоя (сканы) не распознаются: OCR не включён.
- Голосовые сообщения требуют внешнего сервиса транскрипции.
- Нет командных пространств, шаринга и совместной работы.
- Нет rate limiting и refresh-токенов.

**План развития**

- OCR для сканированных PDF и изображений.
- Дайджест сохранённых материалов в Telegram.
- Напоминания «вернуться к этому позже».
- Теги и поиск по нескольким пространствам/проектам.
- Переранжирование результатов (reranker) и кэш эмбеддингов.
- Полноценная production-аутентификация: httpOnly-cookie, refresh-токены, rate limiting.
- Экспорт и импорт библиотеки, резервное копирование.
